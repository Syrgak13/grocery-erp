# ADR-0006. Пессимистические блокировки остатков в фиксированном порядке

**Статус:** предложено (Фаза 3, 27.11.2026) · **Журнал решений:** D-033

## Контекст

BR-041–BR-043, NFR-024: при 10 одновременных продажах последней единицы ровно одна успешна, без взаимных блокировок. Средняя себестоимость тоже требует последовательного обновления.

## Решение

`READ COMMITTED` + `SELECT ... FOR UPDATE`: сначала `product_stock` по возрастанию `product_id`, затем партии по возрастанию `batch.id`; `lock_timeout = 5s`; ошибка → 409 `CONCURRENCY_RETRY`. Последняя линия защиты — `CHECK (qty_on_hand >= 0)`. Порядок одинаков во всех процессах. Логика остаётся в Java; триггеры БД не используются.

## Рассмотренные альтернативы

- **Оптимистические версии** — каскад повторов при конкуренции; используются только для справочников.
- **SERIALIZABLE** — ложные конфликты и повторы.
- **Атомарный UPDATE без блокировок** — не защищает среднюю и план FEFO по нескольким партиям.
- **Триггеры БД для остатков** — логика в двух местах, сложнее тестировать.

## Последствия

Продажи одного товара выполняются последовательно (миллисекунды). Тест конкуренции на Testcontainers обязателен в CI.
