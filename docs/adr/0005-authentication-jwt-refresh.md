# ADR-0005. Аутентификация: access JWT + refresh-токен в httpOnly-cookie

**Статус:** предложено (Фаза 3, 27.11.2026) · **Журнал решений:** D-030

## Контекст

Автор выбрал JWT. Требования Фазы 2 описывают сеанс в cookie (SEC-005) с бездействием 8 ч, абсолютным сроком 24 ч и мгновенным аннулированием при деактивации и смене пароля (FR-005, FR-006). Чистый stateless JWT не умеет отзыв и бездействие.

## Решение

Access JWT (HS256, 15 мин) хранится в памяти SPA и передаётся в `Authorization: Bearer`. Refresh-токен — случайные 256 бит в cookie `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`, в БД хранится SHA-256, ротация при каждом обновлении, повторное использование отзывает цепочку. В токене `token_version`; права читаются из БД с кэшем ≤ 30 с. Пароли — Argon2id. CSRF: Bearer-запросы ему не подвержены; для cookie-маршрутов — SameSite=Strict, обязательный заголовок и проверка Origin.

## Рассмотренные альтернативы

- **Серверная сессия Spring Session в cookie** (как в SEC-005) — проще и надёжнее отзывается, но автор выбрал JWT; кроме того, нужна CSRF-защита всех изменяющих запросов.
- **JWT в `localStorage`** — уязвим к краже через XSS; отклонено.
- **Долгоживущий JWT без refresh** — нельзя отозвать; отклонено.
- **bcrypt (cost 12)** вместо Argon2id — допустим NFR-031, запасной вариант при нехватке CPU.

## Последствия

Нужна таблица `refresh_token` и один запрос к БД (или кэшу) на каждый запрос API — для 3 пользователей на магазин это несущественно. Формулировки SEC-005 и NFR-034 про «cookie сеанса» уточняются (D-030).
