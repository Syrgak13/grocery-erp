# ADR-0007. Идентификаторы bigint и изоляция магазинов составными FK

**Статус:** предложено (Фаза 3, 27.11.2026) · **Журнал решений:** D-032

## Контекст

BR-120–BR-122, DIR-009: данные магазинов в одной БД, обращение к чужому объекту — 404, ссылки между магазинами невозможны.

## Решение

Общая схема, колонка `store_id` в каждой бизнес-таблице, `UNIQUE (store_id, id)` в родителях и составные FK `(store_id, x_id)`. PK — `bigint identity`. Номер документа для пользователя — отдельное поле, сквозное в магазине. `storeId` только из токена.

## Рассмотренные альтернативы

- **Схема на магазин / БД на магазин** — сильнее изоляция, но миграции × N и сложность; отклонено для MVP.
- **Row-Level Security PostgreSQL** — дополнительная защита, но усложняет пул соединений (`SET app.store_id` на транзакцию); можно добавить в R3.
- **UUID v7 как PK** — не раскрывают объём записей, но крупнее индексы и составные ключи; можно ввести как внешние идентификаторы позже.

## Последствия

Последовательные id раскрывают общий порядок записей в системе (не данные). Каждый репозиторий обязан принимать `storeId` — проверяется ArchUnit и тестом изоляции.
