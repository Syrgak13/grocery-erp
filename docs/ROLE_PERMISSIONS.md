## 1. Роли

| Роль | Кто | Назначение |
|---|---|---|
| **OWNER** | Владелец магазина | Полный доступ к данным своего магазина, включая закупочные цены, себестоимость, прибыль, расходы, сотрудников и журнал аудита |
| **STAFF** | Кассир, продавец, старший продавец | Продажи, возвраты текущего дня, просмотр каталога, остатков и сроков **без финансовой информации**. Дополнительные операции — только по делегированию OWNER |

**Делегируемые права STAFF** (включает OWNER для конкретного сотрудника, по умолчанию выключены, FR-015, BR-212):

| Код | Что разрешает | Что остаётся скрытым |
|---|---|---|
| `purchase.receive` | Создавать и проводить приёмки, вводить закупочные цены **в своих документах** | Средняя себестоимость, цены в чужих приёмках, история закупок, суммы по поставщикам, заказы поставщикам |
| `stock.count` | Создавать инвентаризации и быстрые корректировки, вводить фактические количества, проводить документ | Суммы недостач и излишков, себестоимость |
| `stock.writeoff` | Создавать и проводить списания (кроме массового списания истёкших) | Стоимость списаний, отчёт по списаниям |

Роль «управляющий» из исследования Фазы 1 в MVP — это STAFF с нужными делегированными правами (`DECISIONS.md`, D-003).

**Почему приёмка раскрывает цены своего документа.** Чтобы оформить приёмку, сотрудник переписывает цены из накладной поставщика; скрыть их от того, кто их вводит, невозможно. Поэтому право выдаётся только доверенному сотруднику явно, а средняя себестоимость и история цен остаются скрытыми.

## 3. Видимость полей (чувствительные данные)

Поля ниже **исключаются из ответа сервера** для STAFF (BR-211). Они не должны появляться в списках, карточках, поиске, вложенных объектах, сообщениях об ошибках, экспорте и веб-сокетах.

| Поле / данные | Где встречается | OWNER | STAFF | STAFF с `purchase.receive` |
|---|---|---|---|---|
| `unit_cost` закупочная цена партии / строки приёмки | Партии, приёмки, движения | Да | Нет | Только строки своих приёмок |

| `cost_amount` себестоимость строки продажи и возврата | Продажи, возвраты | Да | Нет | Нет |
| `value_at_cost`, `value_at_retail` под риском, «сохранено» | Сроки, риск, панель | Да | Нет | Нет |

## 4. Правила проверки на сервере

1. **Запрещено по умолчанию.** Каждый маршрут API явно объявляет требуемое право; маршрут без объявления не запускается (проверка при старте приложения и в тестах).
2. **Порядок проверки запроса:** аутентификация (401) → определение `store_id` из сеанса (BR-121) → право роли или делегированное право (403) → поиск объекта в пределах `store_id` (404 для чужих, BR-122) → проверка «своё» для STAFF (404) → бизнес-правила (409/422).
3. **Сериализация по роли.** Ответы формируются отдельными схемами для OWNER и STAFF; схема STAFF не содержит полей из раздела 3, поэтому поле нельзя «забыть скрыть».
4. **Делегированные права** читаются из БД при каждом запросе (или из кэша не дольше 60 с), поэтому их отключение действует быстро (BR-212).
5. **Ограничения сумм** (лимит скидки, возвраты только за сегодня) проверяются на сервере при проведении документа, а не в интерфейсе.
6. **Отказы** (403) по чувствительным маршрутам записываются в журнал безопасности с пользователем, маршрутом и временем (Should, R2).
7. **Интерфейс** скрывает недоступные разделы по списку прав из профиля, но это не защита (FR-010).

## 5. Как проверяется матрица

| Проверка | Метод | Критерий |
|---|---|---|
| Каждая строка раздела 2 | Таблица прав хранится в тестах как данные; автотест обходит все маршруты для OWNER, STAFF и STAFF с каждым делегированным правом | 100% маршрутов, ожидаемый код совпадает (NFR-032, AC-AUTH-03) |
| Раздел 3 | Автотест сравнивает схемы ответов STAFF со списком запрещённых полей | 0 запрещённых полей (AC-CAT-06, AC-BATCH-06, AC-INV-03 и др.) |

| Делегирование | Включить/выключить право и повторить запрос | Изменение действует ≤ 60 с (AC-STORE-05) |
