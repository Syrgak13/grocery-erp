# Бизнес-правила

**Фаза 2 · Grocery ERP** · 26.11.2026 · статус: черновик на утверждение

Документ задаёт правила, которые система обязана соблюдать независимо от интерфейса. Все правила проверяются **на сервере**. Идентификаторы `BR-xxx` используются в `REQUIREMENTS.md`, `MVP_SCOPE.md`, `ACCEPTANCE_CRITERIA.md` и `REQUIREMENTS_TRACEABILITY.md`. Нумерация идёт блоками по 10, пропуски оставлены для будущих правил.

Обозначения: **D** — среднесуточные продажи, **L** — срок поставки, **R** — цикл заказа, **SS** — страховой запас, **ROP** — точка заказа, **avg** — средневзвешенная себестоимость единицы.

---

## 1. Себестоимость (метод средневзвешенной стоимости)

> **Метод учёта утверждён в исходном предложении диплома: средневзвешенная себестоимость.** Партионная (фактическая) себестоимость — только предложенная альтернатива, она **не действует** до решения научного руководителя (`DECISIONS.md`, D-002).

| ID | Правило |
|---|---|
| BR-001 | Средневзвешенная себестоимость ведётся **по товару в пределах магазина** (скользящая средняя). При любом **приходе** количества `q` по себестоимости единицы `c`: `avg_new = (Q × avg_old + q × c) / (Q + q)`, где `Q` — остаток товара до прихода по всем партиям. Пример: 10 шт по 50,0000 + 30 шт по 60,00 → 57,5000. |
| BR-002 | **Приходы оцениваются по себестоимости источника:** приёмка — по закупочной цене строки; возврат покупателя — по себестоимости единицы, зафиксированной в исходной строке продажи; отмена списания — по себестоимости единицы из документа списания; излишек инвентаризации — по текущей avg (если avg нет, OWNER вводит цену). |
| BR-003 | **Расходы оцениваются по текущей avg** на момент проведения: продажа, списание, недостача, отмена приёмки. Расход не меняет avg. |
| BR-004 | Если остаток товара `Q = 0`, при следующем приходе `avg_new = c`. При `Q = 0` значение avg хранится последним известным (для оценки излишков). |
| BR-005 | avg хранится с точностью **4 знака** после запятой, округление HALF_UP; денежные суммы движений — 2 знака (BR-071). |
| BR-006 | Каждая партия хранит свою закупочную цену единицы. В методе средневзвешенной стоимости она **информационная** (история цен, будущая альтернатива D-002) и не используется для себестоимости продаж. |
| BR-007 | Себестоимость единицы и сумма себестоимости **фиксируются в строке продажи, возврата, списания и корректировки** в момент проведения и больше не пересчитываются (см. BR-111). |

**Известное ограничение метода (для пояснительной записки):** отмена приёмки по текущей avg (BR-003) не возвращает avg к значению до приёмки, если цены партий различались. Это сознательное упрощение: оно исключает отрицательную стоимость остатка. Решение D-018.

## 2. Запрет отрицательных остатков

| ID | Правило |
|---|---|
| BR-010 | Остаток любой партии никогда не бывает меньше 0. Остаток товара = сумма остатков его партий, следовательно, тоже ≥ 0. |
| BR-011 | Продажа проводится **по принципу «всё или ничего»**: если хотя бы одна строка не может быть полностью обеспечена годными партиями, не проводится ни одна строка. |
| BR-012 | Каждый расходный документ (продажа, списание, недостача, отмена приёмки) проверяет доступность **в той же транзакции**, в которой уменьшает остаток. Предварительная проверка в интерфейсе — только подсказка. |
| BR-013 | Последняя линия защиты — ограничение базы данных `quantity >= 0` на остатке партии. Нарушение ограничения приводит к откату транзакции и ошибке STOCK_INSUFFICIENT. |

## 3. Запрет продажи просроченного товара

| ID | Правило |
|---|---|
| BR-020 | Партия **истекла**, если `сегодня (Asia/Bishkek) > срок годности`. В день, указанный как срок годности, товар считается годным. Правило настраивается в магазине (`block_on_expiry_day`, по умолчанию «нет»), решение D-005. |
| BR-021 | Истёкшая партия не продаётся: FEFO её пропускает, ручной выбор отклоняется (EXPIRED_BATCH), а если у товара нет других годных партий — EXPIRED_ONLY. |
| BR-022 | Товары с признаком «без учёта сроков» имеют партии без срока; правила BR-020 и BR-021 к ним не применяются. |
| BR-023 | Запрет BR-021 действует **и для OWNER**. Единственные допустимые операции с истёкшей партией — списание, инвентаризация и просмотр. |
| BR-024 | Приёмка товара с уже истёкшим сроком запрещена (EXPIRED_ON_RECEIPT). |

## 4. Распределение FEFO

| ID | Правило |
|---|---|
| BR-030 | Порядок выбора партий при расходе: (1) срок годности по возрастанию, пустой срок — в конце; (2) дата приёмки по возрастанию; (3) идентификатор партии по возрастанию. Для товаров без учёта сроков действуют только (2) и (3), то есть FIFO. |
| BR-031 | Если количество строки больше остатка первой партии, строка делится на части по партиям. Сумма частей равна количеству строки. Каждая часть хранит партию, количество, цену и себестоимость. |
| BR-032 | В распределение не входят партии: истёкшие, заблокированные (BLOCKED), с нулевым остатком. |
| BR-033 | Кассир может вручную выбрать партию (например, уценённую). Выбор допускается только для годной, незаблокированной партии с достаточным остатком; он записывается в журнал аудита. Если количество строки больше остатка выбранной партии, остаток распределяется по FEFO. |
| BR-034 | Недостача при инвентаризации без указания партии распределяется по BR-030. Списание всегда указывает партию явно. |
| BR-035 | Возврат покупателя возвращает товар **в ту же партию**, из которой он был продан (связь хранится в строке продажи). |

## 5. Одновременные продажи

| ID | Правило |
|---|---|
| BR-040 | Проведение продажи (и любого расходного документа) — одна транзакция базы данных: проверка остатков, распределение, движения, документ и запись аудита фиксируются вместе или не фиксируются вовсе. |
| BR-041 | Перед изменением остатков транзакция блокирует строки затронутых партий **в детерминированном порядке** (по идентификатору партии), чтобы исключить взаимные блокировки. Другие транзакции по тем же партиям ждут не дольше 5 с. |
| BR-042 | Если ожидание блокировки превысило лимит или произошёл конфликт сериализации, сервер возвращает 409 CONCURRENCY_RETRY. Клиент повторяет запрос с **тем же** ключом идемпотентности не более 3 раз с паузой 0,5 / 1 / 2 с. |
| BR-043 | Гарантия: при N одновременных продажах последней единицы товара успешна ровно одна, остальные получают STOCK_INSUFFICIENT. Проверяется нагрузочным тестом (NFR-024). |

## 6. Идемпотентность продаж

| ID | Правило |
|---|---|
| BR-050 | Клиент создаёт ключ идемпотентности (UUID v4) **при открытии корзины на оплату** и передаёт его с запросом проведения. Ключ уникален в пределах магазина. |
| BR-051 | Повторный запрос с тем же ключом и тем же содержимым возвращает результат первого запроса (тот же номер чека) и ничего не изменяет. |
| BR-052 | Повторный запрос с тем же ключом, но другим содержимым (хеш позиций, количеств, скидок, способа оплаты) отклоняется: 409 IDEMPOTENCY_CONFLICT. |
| BR-053 | Если первый запрос ещё выполняется, повторный получает 409 REQUEST_IN_PROGRESS, и клиент повторяет его позже. Ключи хранятся бессрочно вместе с документом. |
| BR-054 | Те же правила действуют для проведения приёмки, возврата, списания и инвентаризации. |

## 7. Дробные количества

| ID | Правило |
|---|---|
| BR-060 | Единицы измерения: **PCS** (штука), **KG** (килограмм), **L** (литр). |
| BR-061 | Количества хранятся как десятичные числа с 3 знаками после запятой (точность 1 г / 1 мл). Числа с плавающей точкой не используются. |
| BR-062 | Для PCS количество — только целое. Для KG и L минимальное количество 0,001, максимальное в строке 9 999,000. |
| BR-063 | При делении строки между партиями (BR-031) количества частей тоже имеют не более 3 знаков; сумма частей точно равна количеству строки. |
| BR-064 | Сумма строки = `round(количество × цена, 2)` по HALF_UP. Пример: 0,347 кг × 459,00 = 159,273 → 159,27. |

## 8. Денежная точность

| ID | Правило |
|---|---|
| BR-070 | Все деньги — десятичный тип фиксированной точности (например, `NUMERIC`), без плавающей точки, во всех слоях: БД, сервер, API (строка или целые тыйыны), клиент. |
| BR-071 | Суммы и цены хранятся с 2 знаками (1 тыйын = 0,01 сом). Себестоимость единицы — с 4 знаками (BR-005). |
| BR-072 | Режим округления — HALF_UP (коммерческий), одинаковый на сервере и клиенте. |
| BR-073 | Итог документа = сумма округлённых итогов строк. Скидка на чек распределяется по строкам (BR-082), а не вычитается из итога отдельно. |
| BR-074 | Ограничения: цена ≤ 1 000 000,00; сумма чека ≤ 10 000 000,00; сумма расхода ≤ 10 000 000,00. |
| BR-075 | Единственная валюта — KGS (сом). Мультивалютность не поддерживается. |
| BR-076 | Система **не рассчитывает налоги** (НДС, налог с продаж) и не формирует фискальный чек: это функция ККМ (CON-004). |
| BR-077 | Округление наличного расчёта до целого сома **не применяется** в MVP; решение D-006. |

## 9. Скидки

| ID | Правило |
|---|---|
| BR-080 | Виды скидок: (1) ручная на строку — % или сумма; (2) ручная на чек — %; (3) уценка партии (MARKDOWN), заданная OWNER. Промоакции («2 по цене 1», купоны) в MVP отсутствуют. |
| BR-081 | Ручная скидка STAFF не превышает лимита магазина (по умолчанию 10%, настройка 0–50%). Для скидки суммой лимит проверяется как `скидка / сумма строки до ручной скидки`. Для OWNER лимита нет. Проверка — на сервере. |
| BR-082 | Скидка на чек распределяется по строкам пропорционально их суммам после строковых скидок, каждая часть округляется до 0,01; разница округления добавляется к строке с наибольшей суммой. Сумма частей = `round(итог × %, 2)`. |
| BR-083 | Итог строки после всех скидок ≥ 0,00. Итог 0,00 разрешён только OWNER. Скидка больше суммы строки — ошибка DISCOUNT_EXCEEDS_AMOUNT. |
| BR-084 | Уценка партии задаётся ценой единицы, строго меньшей розничной цены товара. Если розничная цена позже стала ниже цены уценки, применяется меньшая. Уценка действует, пока у партии есть остаток или пока OWNER её не снимет. |
| BR-085 | Если цена после скидки ниже avg, OWNER получает предупреждение BELOW_COST; STAFF предупреждение не показывается, потому что раскрывает себестоимость. |
| BR-086 | В строке продажи сохраняются: базовая цена, вид и размер каждой скидки, сумма скидки, итог строки и пользователь, применивший ручную скидку. |

## 10. Возвраты от покупателей

| ID | Правило |
|---|---|
| BR-090 | Возврат оформляется только по исходной продаже этого же магазина. Возврат без чека в MVP не поддерживается. |
| BR-091 | Количество возврата по строке ≤ проданное − уже возвращённое. Для KG/L — с точностью 0,001. |
| BR-092 | Возврат возможен в течение окна возврата (по умолчанию 14 дней от даты продажи, настройка 0–30). Значение по умолчанию — допущение, требует проверки по законодательству КР о защите прав потребителей (D-007). |
| BR-093 | Сумма возврата = `round(итог строки × возвращаемое кол-во / проданное кол-во, 2)`. Последний возврат, закрывающий строку, равен остатку `итог строки − сумма прежних возвратов`, чтобы сумма возвратов точно равнялась итогу строки. |
| BR-094 | Состояние SALEABLE возвращает товар в исходную партию (BR-035). Состояние DAMAGED создаёт возврат и сразу списание с причиной RETURN_DAMAGED. Если исходная партия истекла, состояние принудительно DAMAGED. |
| BR-095 | STAFF оформляет возврат только по продажам текущего дня (Asia/Bishkek); остальные — только OWNER. |
| BR-096 | Возврат уменьшает выручку и себестоимость **периода возврата**; себестоимость возвращённых единиц равна себестоимости единицы в исходной строке продажи (BR-002). Исходная продажа не изменяется. |

## 11. Списания

| ID | Правило |
|---|---|
| BR-100 | Причины: EXPIRED, DAMAGED, SPOILED, SHORTAGE, RETURN_TO_SUPPLIER, OTHER; RETURN_DAMAGED создаётся только системой при возврате. |
| BR-101 | Списание всегда указывает конкретную партию и количество ≤ её остатка. |
| BR-102 | Стоимость списания = количество × avg на момент проведения (BR-003), округление до 0,01; фиксируется в документе. |
| BR-103 | Причина EXPIRED допустима только для истёкших партий; истёкшую партию можно списать с любой причиной. |
| BR-104 | Отмена списания доступна только OWNER, создаёт сторнирующий документ и возвращает количество в ту же партию по себестоимости из документа списания (BR-002); avg пересчитывается по BR-001. |
| BR-105 | Комментарий обязателен для OTHER и SHORTAGE (не короче 3 символов). |
| BR-106 | Массовое списание истёкших создаёт один документ со строкой на каждую истёкшую партию с остатком > 0 и причиной EXPIRED; требует подтверждения с показом количества партий (для OWNER — и суммы). |

## 12. Неизменяемость исторических данных

| ID | Правило |
|---|---|
| BR-110 | Проведённые документы (продажа, возврат, приёмка, списание, инвентаризация) неизменяемы. Ошибки исправляются только новыми документами: возвратом, отменой (сторно), корректировкой. |
| BR-111 | Строки документов хранят «снимок» на момент проведения: название товара (ru и ky), единицу, цену, скидки, себестоимость единицы, партию. Последующие изменения справочников не влияют на прошлые документы и отчёты. |
| BR-112 | Товары, категории, поставщики и пользователи не удаляются физически, если на них есть ссылки; они архивируются (деактивируются). |
| BR-113 | Остатки и avg изменяются только движениями (BR-001–BR-003); нет операций «установить остаток» или «установить себестоимость». |
| BR-114 | Изменяемые записи (расходы, справочники, настройки, права) сохраняют историю изменений в журнале аудита: старое и новое значение, пользователь, время. |
| BR-115 | Пользователи не удаляются, только деактивируются; их имя остаётся в исторических документах. |

| BR-125 | Отчёты, экспорты, фоновые задачи (сверка, пересчёт риска) выполняются отдельно для каждого магазина и не смешивают данные. |

## 15. Страховой запас

| ID | Правило |
|---|---|
| BR-140 | Страховой запас считается в днях продаж: `SS = D × safety_days`. Метод выбран за объяснимость (решение D-012); статистический метод `z × σ × √L` — в будущей версии. |
| BR-141 | `safety_days` задаётся у товара (0–30); если не задан — 2 дня [Д]. |

## 16. Ожидаемые поставки

| ID | Правило |
|---|---|
| BR-150 | Ожидаемая поставка — строка заказа поставщику в статусе ORDERED или PARTIALLY_RECEIVED; ожидаемое количество = заказано − принято. |
| BR-151 | В расчёте пополнения учитываются ожидаемые поставки с ожидаемой датой ≤ сегодня + L + R. |
| BR-152 | Заказ с ожидаемой датой в прошлом считается **просроченным**: он учитывается в расчёте, но объяснение показывает «просрочено на N дн.», а панель — отдельный счётчик. Через 14 дней просрочки [Д] он перестаёт учитываться, пока OWNER не изменит дату. |
| BR-153 | Частичная приёмка уменьшает ожидаемое количество; заказ закрывается автоматически при полном приёме или вручную OWNER (статус CANCELLED для оставшейся части). |

## 17. Риск просрочки

| ID | Правило |
|---|---|
| BR-160 | Для каждой партии товара с учётом сроков и остатком > 0: `days_left = срок годности − сегодня` (в днях, Asia/Bishkek). Число дней, в которые партию ещё можно продавать, включая сегодня: `sell_days = days_left + 1`, если продажа в день срока разрешена (по умолчанию, BR-020), и `sell_days = days_left`, если магазин блокирует продажу в день срока. |
| BR-161 | `D` = проданное количество (продажи − возвраты) за последние 28 полных дней / число дней. Если товар продаётся меньше 28 дней — делитель равен числу дней с первой приёмки (минимум 1); если таких дней < 7 — пометка LOW_DATA. |
| BR-162 | Ожидаемая продажа партий распределяется по FEFO (BR-030): для партий `i = 1..n` по порядку `sold_i = min(q_i, max(0, D × sell_days_i − Σ sold_j, j < i))`. |
| BR-163 | Количество под риском `risk_qty_i = q_i − sold_i`. |
| BR-164 | Стоимость под риском = `risk_qty × avg` (основная, «потери»); справочно — `risk_qty × цена продажи партии` («недополученная выручка»). Обе суммы видит только OWNER. Решение D-019. |
| BR-165 | Уровни: EXPIRED — партия истекла по BR-020 (`sell_days ≤ 0`); CRITICAL — `risk_qty > 0` и `sell_days ≤ T1`; HIGH — `risk_qty > 0` и `sell_days ≤ T2`; MEDIUM — `risk_qty > 0` и `sell_days ≤ T3`; LOW — остальные. По умолчанию T1 = 3, T2 = 7, T3 = 14 дней [Д], решение D-017. |
| BR-166 | Рекомендуемое действие: EXPIRED → списать; CRITICAL → уценить и выложить вперёд, при наличии договорённости — вернуть поставщику; HIGH → выложить вперёд, рассмотреть уценку; MEDIUM → выложить вперёд; LOW → без действия. Действия только рекомендуются. |
| BR-167 | Оценка «сохранено от просрочки» за период = сумма себестоимости единиц, проданных из партий **после** того, как партия получила уровень CRITICAL или HIGH, но не больше `risk_qty` на момент присвоения уровня. Это оценка, а не доказанный эффект; так и подписывается. |

Пример (AC-RISK-01): D = 2 шт/день, партия 10 шт, `sell_days` = 3, avg = 40,0000 → ожидаемая продажа 6, под риском 4, стоимость под риском 160,00, уровень CRITICAL.

## 18. Расчёт пополнения

| ID | Правило |
|---|---|
| BR-170 | `D` — как в BR-161 (28 дней). |
| BR-171 | Точка заказа `ROP = D × L + SS`. Если доступный остаток `A ≤ ROP`, рекомендация помечается URGENT. |
| BR-172 | Целевой запас (политика «заказ до уровня» с периодическим пересмотром): `T = D × (L + R) + SS`. |
| BR-173 | Доступно `A` = остаток годных незаблокированных партий минус количество, которое по BR-162 **не будет продано и истечёт до прихода поставки**, то есть риск партий с `sell_days ≤ L`. Ожидается `E` — по BR-150–BR-152. |
| BR-174 | `need = T − (A + E)`. Если `need ≤ 0`, рекомендации нет. Иначе количество округляется **вверх** до кратности заказа; если результат меньше минимального заказа — берётся минимальный заказ. Для PCS — целое. |
| BR-175 | Для товаров с учётом сроков рекомендованное количество не больше `D × срок годности по умолчанию` (то, что можно продать до истечения новой партии); при срабатывании ограничения объяснение называет причину. |
| BR-176 | Если история продаж < 14 дней, рекомендация помечается LOW_DATA; если `D = 0`, рекомендации нет. |
| BR-177 | Объяснение рекомендации обязательно содержит числа D, период, L, R, safety_days, SS, ROP, T, A (и вычтенное истекающее количество), E (с датами), кратность, ограничения и итог, а также формулу на языке пользователя. |
| BR-178 | Рекомендации носят советующий характер. Система никогда не создаёт и не отправляет заказ без действия пользователя. |

Пример (AC-REPL-01): D = 5, L = 2, R = 7, safety_days = 2 → SS = 10, ROP = 20, T = 55; остаток 18, из них 3 истекут до прихода → A = 15; E = 0 → need = 40 → кратность 12 → **48**; A = 15 ≤ ROP = 20 → URGENT.

## 23. Проверка согласованности правил

| Возможный конфликт | Как разрешён |
|---|---|
| FEFO (BR-030) и ручной выбор партии (BR-033) | Ручной выбор разрешён только для годной партии; остаток строки — по FEFO |

| Лимит скидки (BR-081) и уценка (BR-084) | Лимит касается только ручной скидки; уценку задаёт OWNER |
