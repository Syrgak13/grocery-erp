# Критическая бизнес-логика и алгоритмы

**Фаза 3 · Grocery ERP** · 27.11.2026 · статус: черновик на утверждение

Документ описывает алгоритмы, от которых зависит корректность данных: себестоимость, FEFO, жизненный цикл движений, проведение документов, блокировки, идемпотентность, прибыль, риск просрочки и пополнение. Правила взяты из `BUSINESS_RULES.md` (BR-xxx); здесь они доведены до уровня, по которому можно писать код и тесты.

> **Источник формул.** Исходное предложение диплома так и не было предоставлено (D-015). Все формулы ниже взяты из утверждаемых требований Фазы 2 (`BUSINESS_RULES.md`). Подтверждено автором только одно: метод себестоимости — **средневзвешенный** (D-001). Если в предложении формулы окажутся другими, этот документ нужно сверить с ним до начала Фазы 4.

Все числовые примеры пересчитаны эталонной моделью на `Decimal` с округлением HALF_UP (раздел 13). Каждый пример можно проверить вручную на калькуляторе.

## 1. Физическое распределение и учётная оценка — разные вещи

Это главное архитектурное разграничение документа.

| | Физическое распределение (FEFO) | Учётная оценка (средневзвешенная) |
|---|---|---|
| На какой вопрос отвечает | **Какие** единицы покинули магазин: из какой партии и сколько | **Сколько стоили** эти единицы в учёте |
| Чем определяется | Сроками годности и датами приёмки партий (BR-030) | Скользящей средней себестоимостью товара в магазине (BR-001) |
| Где хранится | `sale_batch_allocation`, `stock_movement.batch_id`, `batch.qty_on_hand` | `product_stock.avg_cost`, `stock_movement.unit_cost`, `sale_item.unit_cost` |
| Модуль | Inventory (`FefoAllocator`) | Inventory (`CostingService`), результат читает Finance |
| Цена партии `batch.unit_cost` | Не используется | **Не используется** для себестоимости продаж (BR-006); только история цен и будущий вариант D-002 |

**Пример.** Партия A — 10 шт по 50,00 (срок 28.11), партия B — 30 шт по 60,00 (срок 05.12). Средняя = 57,5000. Продажа 4 шт:

- физически FEFO берёт 4 шт **из партии A** (раньше срок);
- в учёте себестоимость продажи = 4 × 57,5000 = **230,00**, а не 4 × 50,00 = 200,00.

Цена партии A (50,00) в себестоимость не попадает. Если научный руководитель одобрит партионную себестоимость (D-002), изменится только второй столбец: оценка станет `Σ allocation.qty × batch.unit_cost`. Физическое распределение и модель данных менять не придётся, потому что цена партии уже хранится (BR-006).

## 2. Средневзвешенная себестоимость

### 2.1. Состояние

Для каждой пары (магазин, товар) хранится строка `product_stock`:

| Поле | Тип | Смысл |
|---|---|---|
| `qty_on_hand` | `numeric(12,3)` | `Q` — остаток товара по всем партиям (равен `Σ batch.qty_on_hand`) |
| `avg_cost` | `numeric(14,4)`, может быть `NULL` | Текущая средняя себестоимость единицы; `NULL`, пока не было ни одного прихода |
| `last_purchase_price` | `numeric(14,4)` | Цена последней приёмки (справочно) |

### 2.2. Формулы

**Приход** количества `q > 0` по себестоимости единицы `c ≥ 0` (BR-001, BR-002, BR-004):

```
если Q = 0 или avg_old = NULL:  avg_new = c
иначе:                          avg_new = round4( (Q × avg_old + q × c) / (Q + q) )
Q_new = Q + q
```

Знаменатель `Q + q > 0` всегда, потому что `q > 0` и `Q ≥ 0` (BR-010). Деления на ноль нет.

**Расход** количества `q > 0` (продажа, списание, недостача, отмена приёмки, BR-003):

```
unit_cost = avg_old                  (фиксируется в строке документа и в движении)
cost_amount = round2(q × avg_old)
avg_new = avg_old                    (расход не меняет среднюю)
Q_new = Q − q                        (Q_new ≥ 0 гарантирует CHECK, BR-013)
```

Себестоимость источника для прихода `c` (BR-002):

| Приход | `c` |
|---|---|
| Приёмка (RECEIPT) | Закупочная цена строки приёмки |
| Возврат покупателя (CUSTOMER_RETURN) | `sale_item.unit_cost` исходной строки продажи |
| Отмена списания (WRITE_OFF_REVERSAL) | `write_off_item.unit_cost` исходного списания |
| Излишек инвентаризации (ADJUSTMENT_PLUS) | Текущая `avg_cost`; если она `NULL` — цена, введённая OWNER (обязательна) |

Округление: `round4` — 4 знака HALF_UP для средней (BR-005), `round2` — 2 знака HALF_UP для сумм (BR-071).

### 2.3. Пример 1: штучный товар (проверяется вручную)

| Шаг | Операция | Q до | avg до | Расчёт | Q после | avg после |
|---|---|---|---|---|---|---|
| 1 | Приёмка 10 шт по 50,00 | 0 | NULL | `avg = c` | 10 | 50,0000 |
| 2 | Приёмка 30 шт по 60,00 | 10 | 50,0000 | (10 × 50 + 30 × 60) / 40 = 2 300 / 40 | 40 | **57,5000** |
| 3 | Продажа 15 шт по 80,00 | 40 | 57,5000 | себестоимость = 15 × 57,5 = **862,50**; выручка = 1 200,00 | 25 | 57,5000 |
| 4 | Возврат 5 шт (SALEABLE) | 25 | 57,5000 | `c` = 57,5000 из строки продажи; (25 × 57,5 + 5 × 57,5) / 30 | 30 | 57,5000 |
| 5 | Приёмка 20 шт по 66,00 | 30 | 57,5000 | (30 × 57,5 + 20 × 66) / 50 = 3 045 / 50 | 50 | **60,9000** |

Возврат на шаге 4: сумма возврата = round2(1 200,00 × 5 / 15) = **400,00**, себестоимость возврата = 5 × 57,5000 = **287,50**.

### 2.4. Пример 2: весовой товар

| Шаг | Операция | Расчёт | Результат |
|---|---|---|---|
| 1 | Приёмка 0,800 кг по 450,00 | `avg = c` | avg = 450,0000 |
| 2 | Приёмка 1,000 кг по 470,00 | (0,8 × 450 + 1,0 × 470) / 1,8 = 830 / 1,8 = 461,1111… | avg = **461,1111** |
| 3 | Продажа 1,250 кг по 520,00 | себестоимость = round2(1,25 × 461,1111) = round2(576,388875) | **576,39**; выручка 650,00 |
| 4 | Остаток | 1,8 − 1,25 = 0,550 кг; стоимость = round2(0,55 × 461,1111) | 253,61 |

Проверка: 360,00 + 470,00 − 576,39 = 253,61. Совпадает.

### 2.5. Пограничные случаи

| Случай | Поведение | Правило |
|---|---|---|
| Первый приход, `avg = NULL` | `avg_new = c` | BR-004 |
| `Q = 0` после полной распродажи | `avg` хранится последним известным; следующий приход ставит `avg = c` | BR-004 |
| Закупочная цена 0 (бонус) | Разрешено только с флагом подтверждения; входит в среднюю как 0. Пример: 20 шт по 30,0000 + 4 шт по 0 → **25,0000** | BR-193 |
| Излишек при `avg = NULL` | Сервер требует цену от OWNER, иначе 422 `COST_REQUIRED` | BR-002 |
| Отмена приёмки | Расход по текущей средней. Пример: 10 шт по 50 + 10 шт по 70 → avg 60,0000; отмена второй приёмки списывает 10 шт по **60,00** (600,00), а не по 70,00. Средняя остаётся 60,0000, хотя «истинная» 50,0000 | BR-192, D-018 (известное ограничение) |
| Дрейф округления | Стоимость остатка вычисляется как `Q × avg`, а не накапливается суммой движений, поэтому ошибка округления не растёт. Разница между `Σ cost_amount` движений и `Q × avg` (доли тыйына) показывается в отчёте о стоимости склада строкой «разница округления» | BR-005 |
| Возврат при `Q = 0` | `avg_new = c` из исходной продажи | BR-004 |

## 3. Алгоритм FEFO

### 3.1. Вход и выход

```
allocate(store_id, product_id, qty, today, policy, manual_batch_id?) → список (batch_id, qty) или ошибка
```

`policy.block_on_expiry_day` — настройка магазина (BR-020, D-005).

### 3.2. Шаги

```
1. Партии-кандидаты: batch.store_id = store_id, batch.product_id = product_id,
   batch.status = ACTIVE, batch.qty_on_hand > 0, и
   (expiry_date IS NULL  или  expiry_date > today  или  (expiry_date = today и не block_on_expiry_day)).
   Партии уже заблокированы (FOR UPDATE) вызывающей транзакцией, раздел 7.

2. Если задан manual_batch_id:
     если партии нет среди кандидатов → EXPIRED_BATCH (истекла), BATCH_BLOCKED или BATCH_NOT_FOUND;
     взять t = min(qty, manual.qty_on_hand); qty -= t; записать в аудит (BR-033).

3. Отсортировать оставшихся кандидатов:
     (a) expiry_date ASC, NULL — последними;
     (b) received_at ASC;
     (c) batch.id ASC.
   Для товаров без учёта сроков все expiry_date = NULL, поэтому действует только (b), (c) — FIFO (BR-030).

4. Для каждой партии, пока qty > 0: t = min(qty, b.qty_on_hand); добавить (b.id, t); qty -= t.

5. Если qty > 0:
     если у товара есть истёкшие партии с остатком, а годных нет → EXPIRED_ONLY;
     иначе → STOCK_INSUFFICIENT { available }.
   Вся продажа откатывается (BR-011).
```

Количества — `numeric(12,3)`, вычитание точное; сумма частей всегда равна количеству строки (BR-063). Функция **чистая**: она получает список партий и возвращает план, не обращаясь к базе. Это позволяет проверять её property-based тестом против эталонной реализации (AC-FEFO-07). Та же функция используется для недостач без указания партии (BR-034, AC-FEFO-09), для ожидаемых продаж в оценке риска (BR-162) и в пополнении (BR-173).

### 3.3. Примеры

| Пример | Партии (срок / приёмка / остаток) | Запрос | Результат |
|---|---|---|---|
| AC-FEFO-01 | A 28.11 / — / 2; B 30.11 / — / 5; сегодня 26.11 | 4 шт | A 2, B 2 |
| AC-FEFO-05 | A 0,800 кг; B 1,000 кг (A раньше) | 1,250 кг | A 0,800, B 0,450 |
| Сложный | #7 без срока / 10.11 / 3; #3 30.12 / 15.11 / 3; #5 01.12 / 22.11 / 2; #4 01.12 / 22.11 / 2 | 9 шт | #4 2, #5 2, #3 3, #7 2 |

В «сложном» примере #4 и #5 совпадают по сроку и дате приёмки, порядок решает id; партия без срока идёт последней.

## 4. Жизненный цикл движений запасов

### 4.1. Типы движений

| Тип | Знак | Создаётся | Оценка единицы | Меняет avg |
|---|---|---|---|---|
| RECEIPT | + | Проведение приёмки | Закупочная цена строки | Да |
| RECEIPT_REVERSAL | − | Отмена приёмки | Текущая avg | Нет |
| SALE | − | Проведение продажи (по одному на распределение) | Текущая avg | Нет |
| CUSTOMER_RETURN | + | Проведение возврата | `sale_item.unit_cost` | Да |
| WRITE_OFF | − | Проведение списания | Текущая avg | Нет |
| WRITE_OFF_REVERSAL | + | Отмена списания | `write_off_item.unit_cost` | Да |
| ADJUSTMENT_PLUS | + | Излишек инвентаризации | Текущая avg или цена OWNER | Да (при цене OWNER) |
| ADJUSTMENT_MINUS | − | Недостача инвентаризации | Текущая avg | Нет |

### 4.2. Инварианты

1. Движение **только добавляется**; `UPDATE` и `DELETE` запрещены правами БД (раздел 6 `DATABASE.md`).
2. `batch.qty_on_hand = Σ stock_movement.qty_delta` по партии (DIR-002).
3. `product_stock.qty_on_hand = Σ batch.qty_on_hand` по товару.
4. `batch.qty_on_hand ≥ 0` (CHECK, BR-013).
5. Каждое движение ссылается на документ и строку документа; документ и его движения фиксируются одной транзакцией (DIR-003).
6. `stock_movement.avg_cost_after` хранит среднюю после движения, что позволяет восстановить историю средней и проверить её пересчётом.

Ночная сверка (UC-16, FR-075) проверяет инварианты 2 и 3 для каждого магазина и пишет нарушения в журнал и на панель OWNER. Исправление — только документом инвентаризации; автоматически сверка ничего не меняет.

### 4.3. Статусы партии

```
ACTIVE ──(остаток стал 0)──► DEPLETED ──(возврат/отмена списания вернули остаток)──► ACTIVE
ACTIVE ◄──(OWNER блокирует/разблокирует)──► BLOCKED
```

«Истёкшая» — не статус, а вычисляемое состояние по дате (BR-020), поэтому ночной пересчёт не может «забыть» перевести партию: даже если задача не выполнилась, FEFO сравнивает срок с сегодняшней датой при каждой продаже.

## 5. Рабочие процессы проведения документов

Все процессы ниже выполняются **в одной транзакции** `READ COMMITTED` с явными блокировками (раздел 7). Любая ошибка откатывает всё, включая запись аудита и ключ идемпотентности.

### 5.1. Приёмка (purchase receiving)

```
POST /api/v1/purchases/{id}/post   Idempotency-Key: <uuid>

1. Аутентификация, store_id из токена, право OWNER или purchase.receive (для STAFF — только свой документ).
2. Ключ идемпотентности (раздел 8).
3. SELECT purchase ... FOR UPDATE; статус должен быть DRAFT, иначе 409 DOCUMENT_NOT_DRAFT.
4. Проверка строк: товар активен; qty > 0 и по правилам единицы (BR-062);
   для товара с учётом сроков expiry_date обязателен, expiry_date ≥ today (BR-024, EXPIRED_ON_RECEIPT);
   срок > today + 3 × shelf_life_days (порог — предложение для FR-055) → предупреждение, проведение требует флага confirmSuspiciousExpiry;
   unit_cost = 0 → требует флага confirmZeroCost (BR-193).
5. Заблокировать product_stock затронутых товаров в порядке product_id ASC (INSERT ... ON CONFLICT для новых).
6. Для каждой строки: создать batch (qty_on_hand = qty, unit_cost = c), движение RECEIPT,
   пересчитать avg (раздел 2), обновить last_purchase_price и product_supplier.last_purchase_price.
7. Если приёмка по заказу: purchase_order_item.received_qty += qty; статус заказа PARTIALLY_RECEIVED/RECEIVED (BR-153).
8. purchase.status = POSTED, номер документа, posted_at, posted_by.
9. Аудит PURCHASE_POSTED. Ключ идемпотентности → COMPLETED. COMMIT.
```

Отмена (BR-192): `FOR UPDATE` всех партий приёмки; если у любой партии есть движения кроме RECEIPT — 409 `BATCH_ALREADY_USED`; иначе RECEIPT_REVERSAL по текущей avg, партии → DEPLETED, документ → CANCELLED.

### 5.2. Продажа (POS)

```
POST /api/v1/sales   Idempotency-Key: <uuid>

1. Аутентификация, store_id из токена.
2. Ключ идемпотентности (раздел 8): повтор → вернуть прежний чек; другой хеш → 409 IDEMPOTENCY_CONFLICT.
3. Валидация запроса: 1–100 строк, количества по единицам, скидки в пределах лимита роли (BR-081),
   сумма ≤ 10 000 000,00 (BR-074).
4. Загрузить товары (активные, этого магазина); цену берёт сервер из каталога, цена клиента
   только сверяется: расхождение → 409 PRICE_CHANGED с новыми ценами (клиент показывает и повторяет).
5. Заблокировать product_stock строк чека в порядке product_id ASC, затем партии-кандидаты
   в порядке batch.id ASC (FOR UPDATE, lock_timeout 5 с, BR-041).
6. Для каждой строки — FEFO (раздел 3). Цена распределения = min(розничная, уценка партии) (BR-084).
7. Расчёт денег строки:
     gross = Σ round2(alloc.qty × alloc.price)
     line_discount = ручная скидка строки (% или сумма), ≤ gross (BR-083)
     после скидки чека (BR-082) → line_total ≥ 0
     unit_cost = avg_cost (зафиксировать), cost_amount = round2(qty × unit_cost)
8. Создать sale, sale_item, sale_batch_allocation; уменьшить batch.qty_on_hand, product_stock.qty_on_hand;
   движения SALE (по одному на распределение); DEPLETED для обнулившихся партий.
9. Номер чека из счётчика магазина (document_sequence, блокировка строки в конце транзакции).
10. Аудит: ручные скидки, ручной выбор партии. Ключ → COMPLETED. COMMIT.
11. Ответ 201 с номером чека и итогами (для STAFF — без себестоимости).
```

### 5.3. Возврат покупателя

```
POST /api/v1/returns   Idempotency-Key: <uuid>

1. Права: STAFF — только продажа текущего бизнес-дня (BR-095); OWNER — в окне возврата (BR-092).
2. SELECT sale ... FOR UPDATE (сериализует параллельные возвраты одного чека).
3. Для строки: qty ≤ sold − returned (BR-091).
4. Сумма: если возврат закрывает строку — line_total − Σ прежних возвратов, иначе
   round2(line_total × qty / sold_qty) (BR-093).
5. Выбор партий возврата: распределения строки в порядке, обратном FEFO
   (сначала распределение с наибольшим сроком), в пределах alloc.qty − alloc.returned_qty (D-035).
6. Для каждой части: если партия истекла или condition = DAMAGED → состояние DAMAGED (BR-094).
7. Заблокировать product_stock и партии (по возрастанию id). Движение CUSTOMER_RETURN по
   sale_item.unit_cost; пересчёт avg; партия DEPLETED → ACTIVE при необходимости.
8. Для DAMAGED сразу создать списание RETURN_DAMAGED той же партии (WRITE_OFF по текущей avg).
9. Аудит RETURN_POSTED. Ключ → COMPLETED. COMMIT.
```

Пример (BR-093): строка 3 шт на 100,00. Возвраты по 1 шт: 33,33; 33,33; последний — 100,00 − 66,66 = **33,34**. Сумма возвратов точно 100,00.

### 5.4. Списание

```
POST /api/v1/write-offs   Idempotency-Key: <uuid>

1. Права: OWNER или stock.writeoff; массовое списание истёкших — только OWNER (FR-123).
2. Каждая строка указывает партию (BR-101); qty ≤ batch.qty_on_hand; причина EXPIRED только
   для истёкшей партии (BR-103); комментарий ≥ 3 символов для OTHER и SHORTAGE (BR-105).
3. Блокировки как в 5.2. Движение WRITE_OFF по текущей avg; cost_amount фиксируется (BR-102).
4. Аудит WRITE_OFF_POSTED. COMMIT.
```

Массовое списание (BR-106): сервер сам выбирает все истёкшие партии с остатком > 0 на момент проведения. Клиент передаёт `expectedBatchCount`; если он не совпадает с фактическим, ответ 409 `BATCH_SET_CHANGED` с новым количеством, чтобы пользователь подтвердил актуальный список.

Отмена списания (BR-104): новый документ-сторно, движение WRITE_OFF_REVERSAL в ту же партию по `write_off_item.unit_cost`, пересчёт avg.

### 5.5. Инвентаризация

Ввод факта сохраняет `counted_qty`. При проведении для каждой строки под блокировкой: `diff = counted − qty_on_hand (сейчас)`. Если `qty_on_hand` изменился после ввода (`expected_qty_at_entry ≠ qty_on_hand`), строка возвращается с 409 `COUNT_STALE`, и пользователь подтверждает обе величины (BR-200). Недостача без партии распределяется функцией FEFO (BR-034), излишек без партии создаёт новую партию `source = STOCK_COUNT` (BR-201).

## 6. Расчёт денег в чеке

### 6.1. Порядок

```
1. gross_i      = Σ round2(alloc.qty × alloc.price)            по распределениям строки
2. line_disc_i  = round2(gross_i × pct)  или  сумма              ручная скидка строки
3. net_i        = gross_i − line_disc_i
4. receipt_disc = round2(Σ net_i × receipt_pct)                  скидка чека (BR-082)
   part_i       = round2(net_i × receipt_pct); разница округления добавляется к строке с max net_i
5. total_i      = net_i − part_i ≥ 0                             (BR-083)
6. sale.total   = Σ total_i                                       (BR-073)
```

### 6.2. Пример распределения скидки чека 5%

| Строка | net | part = round2(net × 0,05) | После выравнивания |
|---|---|---|---|
| 1 | 159,27 | 7,96 | 7,96 |
| 2 | 80,00 | 4,00 | 4,00 |
| 3 | 45,50 | 2,28 | 2,28 |
| Итого | 284,77 | 14,24 | round2(284,77 × 0,05) = 14,24 |

Здесь разница округления 0,00; если бы сумма частей отличалась от 14,24, разница добавлялась бы к строке 1 (наибольшая).

### 6.3. Проверка лимита STAFF (BR-081)

Для ручной скидки строки: `line_disc / gross ≤ limit`. Для скидки чека: `receipt_pct ≤ limit`. Если у строки есть обе скидки, лимит проверяется по совокупной ручной скидке строки: `(line_disc + part) / gross ≤ limit`. Это уточнение: BR-081 не описывает сочетание двух скидок, без него STAFF мог бы дать 10% на строку и ещё 10% на чек (D-036).

## 7. Конкурентный доступ к остаткам

### 7.1. Стратегия

Пессимистические блокировки строк в транзакции `READ COMMITTED`:

```
SET LOCAL lock_timeout = '5s';
SELECT ... FROM product_stock WHERE store_id = ? AND product_id IN (...) ORDER BY product_id FOR UPDATE;
SELECT ... FROM batch WHERE store_id = ? AND product_id IN (...) AND qty_on_hand > 0 ORDER BY id FOR UPDATE;
```

1. **Сначала** товары (`product_stock`) по возрастанию `product_id`, **затем** партии по возрастанию `batch.id`. Порядок одинаков во всех процессах (продажа, возврат, списание, приёмка, инвентаризация), поэтому взаимная блокировка невозможна: две транзакции не могут ждать друг друга по кругу.
2. Блокировка `product_stock` сериализует все изменения одного товара. Это нужно не только для остатков, но и для средней: два одновременных прихода иначе потеряли бы одно обновление avg.
3. Ограничение `CHECK (qty_on_hand >= 0)` на `batch` и `product_stock` — последняя линия защиты (BR-013). Нарушение → откат и `STOCK_INSUFFICIENT`.
4. Таймаут блокировки (SQLSTATE `55P03`) или взаимная блокировка (`40P01`) → 409 `CONCURRENCY_RETRY`; клиент повторяет с тем же ключом идемпотентности через 0,5 / 1 / 2 с (BR-042).

### 7.2. Почему не оптимистические блокировки и не SERIALIZABLE

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| Пессимистические `FOR UPDATE` в фиксированном порядке | Предсказуемо; ровно одна из N продаж последней единицы успешна без повторов | Продажи одного товара идут последовательно (несколько мс на транзакцию) | **Выбрано** (ADR-0006) |
| Оптимистическая версия (`@Version`) | Нет ожидания | При конфликте повтор всей продажи; при 10 одновременных продажах — каскад повторов | Используется только для справочников (товар, настройки) |
| `SERIALIZABLE` | Не нужно думать о порядке | Ложные конфликты сериализации на сканах партий; повторы | Отклонено |
| Атомарный `UPDATE batch SET qty = qty − ? WHERE qty >= ?` без блокировок | Просто | Не защищает пересчёт средней и FEFO-план по нескольким партиям | Отклонено |

### 7.3. Проверка (NFR-024)

Интеграционный тест на Testcontainers: товар с остатком 1, 10 потоков одновременно проводят продажу 1 шт с разными ключами. Ожидание: ровно 1 ответ 201, 9 ответов 409 `STOCK_INSUFFICIENT`, `qty_on_hand = 0`, одно движение SALE. Второй тест: 10 000 случайных операций по 20 товарам в 8 потоках — 0 взаимных блокировок, инварианты раздела 4.2 выполняются.

## 8. Идемпотентность

### 8.1. Алгоритм

Ключ вставляется **внутри той же транзакции**, что и документ:

```
BEGIN;
SET LOCAL lock_timeout = '3s';
INSERT INTO idempotency_key (store_id, key, operation, request_hash, status, created_by)
VALUES (?, ?, 'SALE', ?, 'COMPLETED', ?)
ON CONFLICT (store_id, key) DO NOTHING
RETURNING key;
```

| Результат вставки | Что значит | Ответ |
|---|---|---|
| Строка вставлена | Первый запрос | Проводим документ; в конце `UPDATE idempotency_key SET document_id = ?`; COMMIT |
| Конфликт, строка видна | Ключ уже использован и зафиксирован | Хеш совпал → 200 с прежним документом (тот же номер чека, BR-051); хеш другой → 409 `IDEMPOTENCY_CONFLICT` (BR-052) |
| Ожидание > 3 с | Первый запрос с этим ключом ещё в транзакции | 409 `REQUEST_IN_PROGRESS` (BR-053) |

Почему так: уникальный индекс заставляет второй запрос ждать завершения первого. Если первый **зафиксирован**, второй видит его результат. Если первый **откатился** (например, `STOCK_INSUFFICIENT`), строки ключа нет, и второй запрос выполняется как новый. Отдельный статус IN_PROGRESS с «зависшими» ключами после падения процесса не нужен.

### 8.2. Хеш запроса

`request_hash = SHA-256` канонического JSON: строки, отсортированные по порядку в чеке, с полями `productId`, `quantity` (нормализовано до 3 знаков), `manualBatchId`, скидки, `paymentMethod`, `receiptDiscountPct`, `cashReceived`. Поле `clientPrices` в хеш **не входит**, чтобы повтор после `PRICE_CHANGED` был тем же запросом.

### 8.3. Клиент

Ключ создаётся при открытии оплаты (BR-050) и хранится вместе с корзиной в `localStorage`. При сетевой ошибке или 409 `CONCURRENCY_RETRY` / `REQUEST_IN_PROGRESS` клиент повторяет с тем же ключом. После 201/200 корзина и ключ удаляются. Изменение корзины после ошибки создаёт **новый** ключ.

## 9. Валовая и операционная прибыль

### 9.1. Формулы (за период `[from, to]` по бизнес-дате Asia/Bishkek)

```
Выручка брутто     = Σ sale_item.gross                     продажи периода
Скидки             = Σ (line_discount + receipt_discount_part)
Выручка продаж     = Σ sale_item.total
Возвраты (деньги)  = Σ return_item.refund_amount           возвраты периода (BR-096)
Чистая выручка     = Выручка продаж − Возвраты

Себестоимость продаж = Σ sale_item.cost_amount − Σ return_item.cost_amount
Валовая прибыль      = Чистая выручка − Себестоимость продаж          (FR-152)
Валовая маржа, %     = Валовая прибыль / Чистая выручка × 100         (не считается при чистой выручке 0)

Потери               = Σ write_off_item.cost_amount + (Σ недостач − Σ излишков) по инвентаризациям
Расходы              = Σ expense.amount                                 расходы периода
Операционная прибыль = Валовая прибыль − Потери − Расходы               (FR-153)
```

Все слагаемые — уже зафиксированные в строках документов суммы (BR-007), поэтому отчёт за прошлый месяц не меняется после новых приёмок (AC-REP-02).

### 9.2. Пример (ручная проверка)

Продолжение примера 2.3: продажа 15 шт по 80,00 и возврат 5 шт в том же месяце, списание 2 шт, расходы 100,00.

| Строка | Расчёт | Сумма |
|---|---|---|
| Выручка продаж | 15 × 80,00 | 1 200,00 |
| Возвраты | round2(1 200 × 5 / 15) | 400,00 |
| Чистая выручка | 1 200,00 − 400,00 | 800,00 |
| Себестоимость продаж | 862,50 − 287,50 | 575,00 |
| **Валовая прибыль** | 800,00 − 575,00 | **225,00** |
| Списание 2 шт | 2 × 57,5000 | 115,00 |
| Расходы | | 100,00 |
| **Операционная прибыль** | 225,00 − 115,00 − 100,00 | **10,00** |

Проверка AC-REP-03: 100 000,00 − 70 000,00 − 2 000,00 − 15 000,00 = **13 000,00**.

### 9.3. Возврат DAMAGED

Возврат DAMAGED уменьшает себестоимость продаж (как SALEABLE), а потом то же количество списывается с причиной RETURN_DAMAGED и попадает в потери. Итоговое влияние на операционную прибыль = −сумма возврата: покупатель получил деньги, товар пропал. Пример: возврат 1 шт, проданной за 80,00 при avg 57,50: валовая прибыль −80,00 + 57,50 = −22,50; потери +57,50; операционная прибыль −80,00.

### 9.4. Решение, которое нужно подтвердить

FR-153 и AC-REP-03 вычитают только списания. Недостачи и излишки инвентаризации тоже меняют стоимость запасов, и без них прибыль будет завышена при систематических недостачах. Предложение D-037: строка «Потери» = списания + чистые недостачи инвентаризации, с отдельной расшифровкой. Пример AC-REP-03 не меняется (в нём нет инвентаризаций).

## 10. Оценка риска просрочки

### 10.1. Формулы (BR-160–BR-165)

```
D = round4( (Σ проданного − Σ возвращённого за 28 полных дней до сегодня) / N )
    N = 28, если первая приёмка товара была ≥ 28 дней назад; иначе N = max(1, дней с первой приёмки);
    N < 7 → флаг LOW_DATA

Для каждой годной партии товара с учётом сроков, отсортированной по FEFO (раздел 3):
  days_left_i = expiry_date_i − today
  sell_days_i = days_left_i + 1     (продажа в день срока разрешена, по умолчанию)
              = days_left_i         (block_on_expiry_day = true)
  sold_i      = min(q_i, max(0, D × sell_days_i − Σ_{j<i} sold_j))
  risk_qty_i  = q_i − sold_i
  value_at_cost_i   = round2(risk_qty_i × avg_cost)        только OWNER
  value_at_retail_i = round2(risk_qty_i × цена_продажи_i)  только OWNER, справочно

Уровень: sell_days ≤ 0 → EXPIRED; risk_qty > 0 и sell_days ≤ T1 → CRITICAL;
         ≤ T2 → HIGH; ≤ T3 → MEDIUM; иначе LOW.     T1 = 3, T2 = 7, T3 = 14 (D-017)
```

`Σ_{j<i} sold_j` — главное отличие от наивного расчёта: продажи, которые «съест» более ранняя партия, не могут одновременно уменьшить риск поздней партии. Это та же логика FEFO, что и в разделе 3, применённая к прогнозу.

### 10.2. Примеры

**AC-RISK-01.** D = 2, одна партия 10 шт, sell_days = 3, avg = 40,0000: sold = min(10, 6) = 6; риск 4; стоимость 160,00; 3 ≤ T1 → **CRITICAL**.

**AC-RISK-02.** D = 3; A (sell_days 2, 5 шт): sold = min(5, 6) = 5, риск 0. B (sell_days 5, 12 шт): sold = min(12, 15 − 5) = 10, риск **2**.

**Три партии, дробный спрос.** D = 1,5 шт/день, avg = 35,5000, сегодня 26.11, продажа в день срока разрешена:

| Партия | Срок | days_left | sell_days | q | Расчёт sold | sold | risk | Стоимость | Уровень |
|---|---|---|---|---|---|---|---|---|---|
| 1 | 26.11 | 0 | 1 | 4 | min(4, 1,5 × 1 − 0) | 1,5 | 2,5 → **3** | 106,50 | CRITICAL |
| 2 | 29.11 | 3 | 4 | 6 | min(6, 1,5 × 4 − 1,5) | 4,5 | 1,5 → **2** | 71,00 | HIGH |
| 3 | 05.12 | 9 | 10 | 20 | min(20, 15 − 6) | 9 | 11 | 390,50 | MEDIUM |

Для штучных товаров дробный риск (2,5 бутылки) **округляется вверх** до целого (D-038, предложено): лучше предупредить о лишней единице, чем пропустить её. Накопленная сумма `Σ sold` остаётся точной. Для KG/L риск хранится с 3 знаками без округления.

### 10.3. Пограничные случаи

| Случай | Поведение |
|---|---|
| D = 0 (продаж за 28 дней нет) | sold = 0, весь остаток под риском; объяснение «нет продаж за 28 дней» (AC-RISK-03) |
| Продажи меньше 7 дней | N = число дней, флаг LOW_DATA (AC-RISK-04) |
| Возвратов больше продаж за окно | Числитель < 0 → D = 0 |
| Партия заблокирована | Не входит в FEFO-прогноз, весь остаток показывается под риском с причиной BLOCKED |
| Товар без учёта сроков | Риск не считается (BR-022) |
| sell_days > 365 | Расчёт тот же; уровень LOW |
| Уценённая партия | `value_at_retail` по цене уценки |
| Тот же день, разные часы | Бизнес-день по Asia/Bishkek; в 23:59 и 00:01 — разные дни; пересчёт в 00:05 (FR-144) |

### 10.4. «Сохранено от просрочки» (BR-167)

При переходе партии в CRITICAL или HIGH записывается `batch_risk_event(batch_id, level, risk_qty_at_event, event_date)`. За период:

```
saved = Σ по партиям min(risk_qty_at_event, проданное из партии после event_date) × sale_item.unit_cost
```

Пример AC-RISK-07: риск 4 шт в CRITICAL, после уценки продано 4 шт при unit_cost 40,0000 → сохранено 160,00. Это **оценка**, а не доказанный эффект, и подписывается так в интерфейсе.

## 11. Объяснимое пополнение

### 11.1. Формулы (BR-170–BR-177)

```
D                 — как в 10.1
L                 = product_supplier.lead_time_days ?? supplier.lead_time_days ?? store.default_lead_time_days (2)
R                 = supplier.order_cycle_days ?? store.default_order_cycle_days (7)
safety_days       = product.safety_days ?? store.default_safety_days (2), для товаров со сроком ≤ floor(shelf_life_days / 2)
SS  = D × safety_days
ROP = D × L + SS
T   = D × (L + R) + SS
A   = остаток годных незаблокированных партий − Σ risk_qty_i для партий с sell_days_i ≤ L
E   = Σ (ordered − received) по строкам заказов ORDERED / PARTIALLY_RECEIVED
      с expected_date ≤ today + L + R и просрочкой не больше 14 дней (BR-151, BR-152)
need = T − (A + E)
если need ≤ 0 → рекомендации нет
иначе rec = ceil(need / multiple) × multiple; если rec < min_order_qty → rec = min_order_qty
для товара со сроком: cap = D × shelf_life_days; если rec > cap → rec = floor(cap / multiple) × multiple (D-039)
PCS → целое; URGENT, если A ≤ ROP; LOW_DATA, если история < 14 дней; D = 0 → рекомендации нет
```

### 11.2. Примеры (проверяются вручную)

**AC-REPL-01.** D = 5, L = 2, R = 7, safety_days = 2, кратность 12. Партии: X — 8 шт, sell_days 1; Y — 10 шт, sell_days 20.

| Шаг | Расчёт | Результат |
|---|---|---|
| SS | 5 × 2 | 10 |
| ROP | 5 × 2 + 10 | 20 |
| T | 5 × (2 + 7) + 10 | 55 |
| Риск X | sold = min(8, 5 × 1) = 5 → риск 3; sell_days 1 ≤ L → вычитается | 3 |
| Риск Y | sold = min(10, 5 × 20 − 5) = 10 → риск 0 | 0 |
| A | 18 − 3 | 15 |
| E | нет заказов | 0 |
| need | 55 − (15 + 0) | 40 |
| rec | ceil(40 / 12) × 12 = 4 × 12 | **48** |
| URGENT | 15 ≤ 20 | да |

**AC-REPL-02.** То же и заказ 24 шт в горизонте: need = 55 − (15 + 24) = 16 → ceil(16 / 12) × 12 = **24**.

**AC-REPL-04.** Срок годности 5 дней, кратность 1: cap = 5 × 5 = 25; rec 40 → **25**. С кратностью 12: rec 48 → cap 25 → floor(25 / 12) × 12 = **24** (D-039).

**Дробный спрос и минимальный заказ.** D = 3,25; L = 3; R = 7; safety_days = 2; кратность 6; минимальный заказ 24; партии 4 шт (sell_days 2) и 10 шт (sell_days 30).
SS = 6,50; ROP = 16,25; T = 39,00. Риск первой партии: sold = min(4, 6,5) = 4, риск 0 → A = 14. need = 25,00 → ceil(25 / 6) × 6 = **30** ≥ 24. URGENT, так как 14 ≤ 16,25.

### 11.3. Объяснение

Сервер возвращает объяснение **структурой**, а не текстом (FR-208):

```json
{ "code": "REPLENISHMENT_EXPLANATION",
  "params": { "D": "5.0000", "periodDays": 28, "L": 2, "R": 7, "safetyDays": 2, "SS": "10.000",
              "ROP": "20.000", "T": "55.000", "stock": "18.000", "expiringBeforeDelivery": "3.000",
              "A": "15.000", "E": "0.000", "expected": [], "need": "40.000", "multiple": "12",
              "minOrder": "0", "cap": null, "result": "48", "flags": ["URGENT"] } }
```

Клиент собирает текст по шаблону ресурса `replenishment.explanation` на русском. Проверка AC-REPL-05: `T − A − E = need`, `ceil(need / multiple) × multiple = result`.

### 11.4. Пограничные случаи и вопросы

| Случай | Поведение |
|---|---|
| Кратность не задана | multiple = 1 (для PCS) или 0,001 (для KG/L) |
| cap < min_order_qty | Рекомендация = cap, флаг `MIN_ORDER_EXCEEDS_SHELF_LIFE`; OWNER решает сам (D-039) |
| cap = 0 после округления вниз | Рекомендация 0 с тем же флагом |
| Заказ просрочен > 14 дней | Не входит в E, отдельный счётчик на панели (BR-152) |
| Партии со sell_days > L, но риском > 0 | По BR-173 не вычитаются из A. Это упрощение: часть их остатка может истечь до конца цикла R. Уточнение (вычитать риск с sell_days ≤ L + R) записано как вопрос в D-039 |
| D < 0,0001 | Округляется до 0 → рекомендации нет |
| Товар в архиве | Не рассчитывается |
