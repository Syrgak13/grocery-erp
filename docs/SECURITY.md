# Архитектура безопасности

**Фаза 3 · Grocery ERP** · 27.11.2026 · статус: черновик на утверждение

Документ описывает аутентификацию, авторизацию, изоляцию магазинов и защиту веб-приложения, а также модель угроз STRIDE. Требования-источники: SEC-001–SEC-013, NFR-030–NFR-036, `ROLE_PERMISSIONS.md`. Целевой уровень — OWASP ASVS 4.0 уровень 1 (NFR-034).

---

## 1. Границы доверия

```
[Браузер] ──HTTPS──► [Nginx: TLS, заголовки, лимиты] ──HTTP, сеть Docker──► [Backend] ──► [PostgreSQL]
                                                                                │
                                                          [Резервные копии, зашифрованы] ──► [Внешнее хранилище]
```

| Граница | Кто по ту сторону | Доверие |
|---|---|---|
| Интернет → Nginx | Любой, включая злоумышленника | Нет |
| Nginx → Backend | Только Nginx в сети Docker; порт backend не публикуется | Транспорт доверенный, запрос — нет |
| Backend → PostgreSQL | Роль `grocery_app` с минимальными правами | Ограниченное |
| Сервер → внешнее хранилище копий | Провайдер хранилища | Не доверяем содержимое — копии зашифрованы |
| GitHub Actions → сервер | Конвейер развёртывания | Только ключ развёртывания с ограниченной командой |

Диаграммы: [`diagrams/deployment.md`](diagrams/deployment.md), [`diagrams/sequence-auth.md`](diagrams/sequence-auth.md).

## 2. Аутентификация

### 2.1. Пароли

| Параметр | Значение | Требование |
|---|---|---|
| Алгоритм | **Argon2id** (`Argon2PasswordEncoder` Spring Security, параметры OWASP: память 19 МиБ, итерации 2, параллелизм 1, соль 16 байт) | NFR-031, SEC-004 |
| Зависимость | `org.bouncycastle:bcprov-jdk18on` (нужна `Argon2PasswordEncoder`) | Добавляется в Фазе 4 |
| Длина | 8–128 символов, любые символы Unicode, без требований к составу | ASVS V2.1 |
| Запрещённые пароли | Список 10 000 распространённых паролей; пароль, равный логину | ASVS V2.1.7 |
| Хранение | Только хеш в формате PHC (`$argon2id$v=19$m=19456,t=2,p=1$...`) | |
| Журналы | Пароль не логируется ни в каком виде; тело `/auth/*` не пишется в журнал | NFR-031 |
| Временный пароль | Генерируется сервером (12 символов), флаг `must_change_password` — смена при первом входе | FR-008, FR-013 |

Альтернатива — bcrypt с cost 12 (встроен, без BouncyCastle). Argon2id выбран, потому что устойчив к перебору на GPU; при проблемах с производительностью на сервере 2 vCPU допустим переход на bcrypt — NFR-031 разрешает оба (ADR-0005).

### 2.2. Вход и защита от подбора

1. Логин приводится к нижнему регистру и ищется в `app_user`.
2. Если пользователь не найден, сервер всё равно вычисляет хеш фиктивного пароля — время ответа не выдаёт, существует ли логин.
3. Ошибка всегда одна: 401 `AUTH_INVALID_CREDENTIALS`.
4. 5 неудач подряд за 15 минут → `locked_until = now + 15 мин`, 423 `AUTH_LOCKED` (FR-003). Успешный вход обнуляет счётчик.
5. Nginx ограничивает `/api/v1/auth/login` до 10 запросов в минуту с IP (SEC-008), backend — то же через Bucket4j на случай обхода.
6. Каждая попытка пишется в аудит: `LOGIN_SUCCESS` / `LOGIN_FAILED` с IP и User-Agent.

Известный риск: злоумышленник может намеренно заблокировать учётную запись OWNER, зная логин. Последствия ограничены 15 минутами; лимит по IP замедляет атаку; OWNER видит события в аудите. Принимается для MVP (угроза D-2 в разделе 9).

### 2.3. Токены

Решение D-030 (ADR-0005): **короткоживущий access JWT в памяти браузера + непрозрачный refresh-токен в httpOnly-cookie, хранящийся в БД**. Это выполняет требования автора (JWT) и сохраняет свойства серверного сеанса из FR-005, FR-006 и SEC-005: отзыв, бездействие 8 ч, абсолютный срок 24 ч.

| | Access-токен | Refresh-токен |
|---|---|---|
| Формат | JWT, HS256, ключ 256 бит из окружения | 256 бит из `SecureRandom`, base64url; в БД — только SHA-256 |
| Где у клиента | Переменная в памяти JS (не `localStorage`) | Cookie `refresh_token`: `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth` |
| Срок | 15 минут | Бездействие 8 ч (`last_used_at`), абсолютный 24 ч от входа (`family_expires_at`) |
| Как передаётся | `Authorization: Bearer` | Автоматически браузером только на `/api/v1/auth/*` |
| Отзыв | Через `token_version` пользователя (ниже) | `revoked_at` в БД |

Утверждения (claims) access-токена: `iss = grocery-erp`, `aud = grocery-erp-api`, `sub = userId`, `store = storeId`, `role`, `tv = token_version`, `jti`, `iat`, `exp`. Права (`purchase.receive` и др.) **не кладутся** в токен: они читаются из БД, чтобы отключение действовало сразу (BR-212).

Почему HS256, а не RS256: токен выпускает и проверяет один и тот же процесс, публичный ключ никому не нужен. Ротация ключа: в окружении два ключа (`JWT_SECRET_CURRENT`, `JWT_SECRET_PREVIOUS`) с `kid` в заголовке; старый принимается 15 минут после ротации.

### 2.4. Проверка каждого запроса

```
1. Spring Security OAuth2 Resource Server проверяет подпись, exp, iss, aud (NimbusJwtDecoder).
2. PrincipalLoader по sub загружает (кэш Caffeine, TTL 30 с, сброс при изменении пользователя):
     active, token_version, role, store_id, permissions.
3. Отказ 401, если пользователь не активен или tv в токене ≠ token_version.
4. CurrentUser(userId, storeId, role, permissions) кладётся в SecurityContext.
```

Приложение работает в одном экземпляре, поэтому сброс кэша при изменении пользователя действует **мгновенно**; 30 с — страховка, укладывающаяся в 60 с из BR-212.

### 2.5. Ротация refresh-токена и обнаружение повторного использования

```
POST /api/v1/auth/refresh  (cookie refresh_token, заголовок X-Requested-With)
1. Найти запись по SHA-256 токена. Нет → 401.
2. Запись отозвана с причиной ROTATED → это повторное использование украденного токена:
     отозвать всю цепочку (family_id), аудит AUTH_REFRESH_REUSED, 401.
3. now − last_used_at > 8 ч или now > family_expires_at или пользователь неактивен → 401.
4. Отозвать текущую (ROTATED), выпустить новую в той же цепочке, новый access-токен. 200 + Set-Cookie.
```

Несколько вкладок: клиент выполняет refresh под `navigator.locks.request('auth-refresh')`, поэтому две вкладки не отправят один и тот же токен одновременно (иначе сработало бы обнаружение повтора).

### 2.6. Когда сеансы аннулируются (FR-006)

| Событие | Действие |
|---|---|
| Выход | Отзыв текущей цепочки, удаление cookie |
| «Выйти на всех устройствах» | `token_version + 1`, отзыв всех цепочек |
| Деактивация сотрудника | `token_version + 1`, отзыв всех цепочек, сброс кэша |
| Смена или сброс пароля | То же; текущему пользователю при смене выдаются новые токены |
| Изменение делегированных прав | Сброс кэша прав (токены остаются — права в них не хранятся) |
| Обнаружен повтор refresh | Отзыв цепочки |

## 3. Авторизация

### 3.1. Роли и права

Две роли (OWNER, STAFF) и три делегированных права STAFF (`purchase.receive`, `stock.count`, `stock.writeoff`) — `ROLE_PERMISSIONS.md`. Реализация:

1. **Запрещено по умолчанию.** `SecurityFilterChain` требует аутентификацию для `/api/**`, кроме трёх публичных маршрутов. Каждый метод контроллера имеет аннотацию `@RequiresRole` или `@RequiresPermission`; тест при старте контекста находит методы без аннотации и падает (SEC-001).
2. **Проверка в сервисе**, а не только на маршруте, для правил, зависящих от данных: «STAFF — только свои приёмки», «возврат — только чек сегодняшнего дня», «лимит скидки». Это защищает и при вызове сервиса из другого маршрута.
3. **Сериализация по роли** — раздельные DTO (ARCHITECTURE, раздел 5.6).
4. Отказы 403 по маршрутам OWNER пишутся в аудит как `ACCESS_DENIED` (ROLE_PERMISSIONS §4.6).

### 3.2. Изоляция магазинов и защита от IDOR

| Уровень | Мера |
|---|---|
| Вход данных | `storeId` берётся только из `CurrentUser`; в DTO запросов поля `storeId` нет, неизвестные поля JSON отклоняются (`FAIL_ON_UNKNOWN_PROPERTIES = true`) — защита от mass assignment |
| Репозитории | Каждый метод принимает `storeId`; запросы вида `WHERE store_id = :storeId AND id = :id`. Правило ArchUnit запрещает `findById` без `storeId` для бизнес-таблиц |
| Ответ | Чужой объект → 404 `NOT_FOUND`, неотличимый от несуществующего (BR-122) |
| «Своё» для STAFF | Чужая приёмка или чек → тоже 404 |
| БД | Составные FK `(store_id, x_id)` не позволяют связать объекты разных магазинов даже при ошибке в коде (DIR-009) |
| Фоновые задачи | Цикл по магазинам; каждый проход получает свой `storeId` (BR-125) |
| Тест | Два магазина в тестовой БД; автотест вызывает **каждый** маршрут из OpenAPI с id объектов чужого магазина → только 404 (NFR-033) |

Последовательные `bigint`-идентификаторы не дают доступа к чужим данным, но раскрывают примерный общий объём записей в системе. Для MVP это принято (ADR-0007); переход на UUID v7 возможен для внешних идентификаторов без изменения FK.

## 4. Защита входных данных

| Угроза | Мера |
|---|---|
| Некорректные данные | Bean Validation на DTO (`@NotNull`, `@Size`, `@Digits`, `@DecimalMin`), собственные ограничения `@Quantity(unit)`, `@Money`. Бизнес-правила — в сервисах. Клиентская Zod-валидация — только подсказка |
| SQL-инъекции | Spring Data JPA и параметризованные запросы; конкатенация SQL запрещена (правило ревью и Semgrep/CodeQL в CI) (SEC-007) |
| XSS | React экранирует вывод; `dangerouslySetInnerHTML` запрещён ESLint; CSP (раздел 6) |
| Подмена цен клиентом | Цена всегда берётся с сервера; цена клиента только сверяется (`PRICE_CHANGED`) |
| Размер запроса | Nginx `client_max_body_size 1m`, для импорта — 5m; не более 100 строк в чеке, 200 в списании |
| Импорт CSV/XLSX | Ограничения Apache POI на коэффициент сжатия (zip-бомба), ≤ 5 000 строк, только ожидаемые колонки |
| CSV-инъекция при экспорте | Ячейки, начинающиеся с `=`, `+`, `-`, `@`, префиксуются апострофом |
| Подделка порядка операций | Проведение только из статуса DRAFT; повтор — идемпотентность |
| Числа | `BigDecimal` с проверкой масштаба; `NaN`, экспонента и `float` в JSON отклоняются (деньги — строки) |

## 5. CORS и CSRF

**CORS.** Frontend и API на одном домене (`https://<домен>/` и `https://<домен>/api/v1`), поэтому CORS **не включается**: браузер блокирует междоменные запросы к API по умолчанию. В разработке Vite проксирует `/api` на backend. Если в будущем появится отдельный домен — белый список из одного origin (SEC-006).

**CSRF.** Большинство запросов несут access-токен в заголовке `Authorization`, который браузер не добавляет автоматически, — CSRF к ним неприменим. Единственное, что браузер шлёт автоматически, — cookie refresh-токена на `/api/v1/auth/*`. Для этих маршрутов:

1. `SameSite=Strict` — cookie не отправляется с других сайтов;
2. обязательный заголовок `X-Requested-With: grocery-erp` (простая HTML-форма не может его добавить);
3. проверка заголовка `Origin` (или `Referer`) на совпадение с собственным доменом.

Встроенная CSRF-защита Spring Security отключается для `/api/**`, потому что её заменяют эти меры (ADR-0005). Требование SEC-006 «защита от CSRF для изменяющих запросов» выполнено, формулировка NFR-034 про cookie сеанса уточняется в D-030.

## 6. Транспорт и заголовки

Настраиваются в Nginx (`infra/nginx`):

| Заголовок / параметр | Значение |
|---|---|
| TLS | Только TLS 1.2 и 1.3, сертификат Let's Encrypt (certbot), OCSP stapling (NFR-030) |
| HTTP → HTTPS | 301 на всех путях |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` |
| `Content-Security-Policy` | `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self'; font-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'; form-action 'self'` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` |
| `Cache-Control` | `no-store` для `/api/**`; длительный кэш для статики с хешем в имени |
| Версия сервера | `server_tokens off` |

`'unsafe-inline'` в `style-src` нужен, потому что компоненты Radix (основа shadcn/ui) задают позиционирование через атрибут `style`. Скрипты inline запрещены, поэтому риск XSS через стили низкий.

## 8. Секреты, журналы, ошибки, аудит

### 8.1. Секреты (SEC-010)

| Секрет | Где хранится |
|---|---|
| Пароли ролей БД, `JWT_SECRET_*`, код приглашения | Файл `.env` на сервере (`chmod 600`, владелец — служебный пользователь); в репозитории только `.env.example` без значений |
| Публичный ключ шифрования копий (age) | `.env` на сервере |
| Приватный ключ копий | **Не на сервере**: у автора офлайн и в менеджере паролей |
| SSH-ключ развёртывания | GitHub Actions Secrets, ключ ограничен командой в `authorized_keys` |
| Учётные данные внешнего хранилища копий | `.env` на сервере, ключ с правом только записи в один бакет |

CI: `gitleaks` на каждый push (NFR-035). Секреты не передаются в образы Docker при сборке.

### 8.2. Безопасная обработка ошибок (SEC-013)

- Ответ 500 — только `code: INTERNAL_ERROR`, `requestId`, без стека, SQL, имён классов.
- Исключения БД (`DataIntegrityViolationException`) преобразуются в понятные коды по имени ограничения (`chk_batch_qty_non_negative` → `STOCK_INSUFFICIENT`), остальные — в 500.
- Ошибки аутентификации не раскрывают, существует ли логин.
- `server.error.include-stacktrace=never`, `include-message=never`.

### 8.3. Журнал приложения

JSON в stdout: время, уровень, `requestId`, `storeId`, `userId`, маршрут, статус, длительность. Не пишутся: пароли, токены, cookie, тела запросов `/auth/*`, полные тела продаж. Значения из запроса экранируются JSON-кодировщиком (защита от подделки строк журнала).

### 8.4. Журнал аудита (SEC-009)

События FR-211 пишутся **в той же транзакции**, что и действие: если запись аудита не удалась, действие откатывается (AC-AUD-05). Приложение не имеет прав `UPDATE`/`DELETE` на `audit_log` (DATABASE, раздел 6). Хранение ≥ 1 года (в MVP — бессрочно). В `old_value`/`new_value` никогда не попадают пароли, хеши и токены.

## 9. Модель угроз (STRIDE)

Оценка: **В** — высокий риск, **С** — средний, **Н** — низкий (вероятность × ущерб для пилота до 10 магазинов).

### 9.1. Spoofing — подмена личности

| ID | Угроза | Риск | Меры | Остаточный |
|---|---|---|---|---|
| S-1 | Подбор пароля | В | Argon2id, блокировка 5/15 мин, лимит по IP, запрещённые пароли | Н |
| S-2 | Кража access-токена через XSS | С | Токен только в памяти, живёт 15 мин; CSP без inline-скриптов; React-экранирование | Н |
| S-3 | Кража refresh-токена | С | httpOnly + Secure + SameSite=Strict, путь `/api/v1/auth`; ротация с обнаружением повтора | Н |
| S-4 | Подделка JWT | С | HS256 с ключом 256 бит, проверка `iss`, `aud`, `exp`, запрет `alg: none` (Nimbus) | Н |
| S-5 | Кассир работает под учётной записью владельца (общий пароль) | С | Отдельные учётные записи бесплатно в пределах 10; аудит входов по устройствам; обучение | С (организационная) |
| S-6 | Подмена оператора при сбросе пароля OWNER | С | Сброс только CLI на сервере после проверки личности (D-011), запись в аудит | Н |

### 9.2. Tampering — изменение данных

| ID | Угроза | Риск | Меры | Остаточный |
|---|---|---|---|---|
| T-1 | Подмена цены или скидки в запросе кассы | В | Цены с сервера; лимит скидки на сервере (BR-081); аудит ручных скидок | Н |
| T-2 | Подмена `storeId` или id чужого объекта (IDOR) | В | Раздел 3.2; тест изоляции всех маршрутов | Н |
| T-3 | Изменение проведённого документа | С | Нет маршрутов изменения; права БД; исправление только сторно (BR-110) | Н |
| T-4 | Изменение журнала аудита | С | Нет `UPDATE`/`DELETE` у роли приложения | Н (кроме администратора сервера) |
| T-5 | SQL-инъекция | С | Параметризованные запросы, CodeQL | Н |
| T-6 | Отрицательный остаток через гонку запросов | В | Блокировки строк + CHECK (ALGORITHMS, раздел 7) | Н |
| T-7 | Подмена образа или зависимости (цепочка поставок) | С | Actions закреплены по SHA, Dependabot, `npm ci` по lock-файлу, Trivy для образов, образы из GHCR с digest | Н |

### 9.3. Repudiation — отказ от действий

| ID | Угроза | Риск | Меры | Остаточный |
|---|---|---|---|---|
| R-1 | Сотрудник отрицает возврат, скидку или списание | С | Аудит с пользователем, временем, IP, значениями; документ хранит автора | Н |
| R-2 | Совместное использование учётной записи | С | См. S-5 | С |
| R-3 | Удаление следов администратором сервера | Н | Ежедневные копии вне сервера содержат журнал; единственный администратор — автор | Н |

### 9.4. Information disclosure — раскрытие информации

| ID | Угроза | Риск | Меры | Остаточный |
|---|---|---|---|---|
| I-1 | STAFF видит закупочные цены и прибыль | В | Раздельные DTO, тест схем STAFF, сообщения об ошибках без скрытых полей (BR-211) | Н |
